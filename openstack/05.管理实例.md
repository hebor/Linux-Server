## 一、创建实例

### 1、创建Flavor

flavor的类似于模板的概念，flavor定义了实例的资源用量，在OpenStack上新建实例之前必须要先创建flavor，在创建的flavor上指定虚拟硬件资源，例如vCPU、vMEM、vDisk等，再通过flavor创建实例，通过flavor创建的实例所具备的虚拟硬件资源量就等同于flavor的虚拟资源量

在OpenStack的概念里，flavor指的是虚拟机实例的类型，创建flavor时会需要指定一个“根磁盘容量”，这个根磁盘容量的大小不可小于image文件的Virtual size。且flavor的创建只能通过admin账号、或具备admin角色权限的账号进行创建。例如，通过admin账户创建要给flavor之前，需要先确认磁盘镜像的信息

```bash
[root@controller ~]# source admin-openrc
[root@controller ~]# qemu-img info cirros-0.4.0-x86_64-disk.img 
image: cirros-0.4.0-x86_64-disk.img
file format: qcow2
virtual size: 44M (46137344 bytes)    # 创建flavor时，flavor的跟磁盘容量不可小于此容量
disk size: 12M
cluster_size: 65536
Format specific information:
    compat: 1.1
    lazy refcounts: false
    refcount bits: 16
    corrupt: false
```

安全组简单一点理解就是一组规则的集合，这组规则定义了对实例进、出的流量的处理方式，例如，可以实现定义外部流量只能访问到实例的Web服务，而不可以访问到实例的ssh服务

## 二、实例控制台

在web控制台中直接点击实例名称即可查看实例详细信息，查看实例的详细信息可以通过控制台（即VNC）的方式访问实例，但根据现有的配置文件，windows主机无法直接访问到实例的控制台页面，因为windows主机本地无法解析域名`controller:6080`。这个问题可以通过多种方式解决，例如，通过本地DNS服务器或windows本地Hosts解析，使windows主机具备`controller:6080`的域名解析，或者通过修改Compute节点的Nova服务的配置文件，将VNC的跳转地址配置为具体的IP而非域名

   ![Web实例控制台-1](./image/Web实例控制台-1.png)

### 1、Windows主机无法访问VNC控制台问题

1. 修改Compute节点的Nova服务配置文件，将VNC代理URL的域名修改为固定IP，这样windows主机在进入实例的控制台时会访问固定IP而非域名，此方式无需配置windows主机的域名解析

   ```bash
   [root@compute ~]# vim /etc/nova/nova.conf
   [vnc]
   novncproxy_base_url = http://192.168.0.40:6080/vnc_auto.html    # 将此处URL的域名修改为IP
   
   [root@compute ~]# systemctl restart openstack-nova-compute
   ```

2. 修改Compute节点的Nova服务中有关于VNC的配置后，重启Nova服务，再刷新浏览器会发现控制台已经产生变化，但仍提示connection is closed

   ![Web实例控制台-3](./image/Web实例控制台-3.png)

### 2、控制台连接失败问题

1. 在Controller节点查看novncproxy的日志

   通过novncproxy日志初步判断可能是由于`noVNC` 客户端与`nova-novncproxy`组件之间的WebSocket协议协商失败，导致浏览器无法建立VNC连接

   ```bash
   [root@controller ~]# tail -f /var/log/nova/nova-novncproxy.log
   2025-05-28 20:32:05.934 5164 INFO nova.console.websocketproxy [-] 192.168.0.1 - - [28/May/2025 20:32:05] code 400, message Client must support 'binary' or 'base64' protocol
   ```

2. 编辑`/usr/share/novnc/core/websock.js`文件，强制声明支持`binary`或`base64`协议

   ```bash
   [root@controller ~]# vim /usr/share/novnc/core/websock.js
   	open(uri, protocols) {    # 约在230行左右
   		this.attach(new WebSocket(uri, ['binary', 'base64']));    # 显式添加协议参数
   	}
   [root@controller ~]# systemctl restart openstack-nova-novncproxy
   ```

   禁用浏览器缓存数据并刷新浏览器，能够正常访问到VNC控制台

   ![Web实例控制台-4](./image/Web实例控制台-4.png)

### 3、实例无法正常启动问题

虽然已经能够通过VNC控制台管理实例，但实例本身无法进入系统，这是由于实验环境中的嵌套虚拟化导致的，使用物理设备时不会有这种问题。这个问题可以通过多种方式解决，例如，手动修改image的虚拟化硬件属性，设置image不使用virtio驱动

```bash
[root@controller ~]# openstack image set --property hw_disk_bus=ide --property hw_vif_model=e1000 cirros
```

- hw_disk_bus=ide

  将虚拟机的磁盘控制器类型设置为IDE，这是一种传统磁盘接口标准，适用于兼容旧版操作系统，IDE总线性能较低，但兼容性更好

- hw_vif_model=e1000

  将虚拟机的网卡类型指定为Intel E1000型号，这是一种广泛支持的硬件模拟网卡，适用于需要兼容性或未安装virtio-net驱动的GuestOS，E1000基于全虚拟化，性能低于virtio-net，但通用性更强。如果GuestOS支持virtio-net，建议优先使用virtio-net提高吞吐量

修改image的虚拟化硬件属性后，需要重新创建实例，重新创建的实例则恢复正常

## 三、创建外部网络

通过VNC控制台登录实例后，查看实例的IP，实例通过private网络自动获取到了DHCP地址池中的IP，但此时VM1实例仍是一个信息孤岛，它无法与其他网络实现通信。网络的一个基本知识是，如果要实现跨网段通信，需要具备一个路由设备，因此还需要为VM1实例创建一个Router，但一个虚拟路由器仍无法真正意义上的实现跨网段通信，因此该Router还需要桥接到一个真正的物理网络上

![实例网络-1](./image/实例网络-1.png)

实际上，通过Web控制台创建private网络时，底层同步在Neutron节点和Compute节点上创建了一个网桥，并且vxlan-1绑定到了这个网桥上。此前在安装部署Neutron服务时，在linux bridge agent插件的配置文件中有声明vxlan隧道的源ip，那么在Compute节点上可以实现，VM1实例接入private网络，并通过vxlan隧道将数据转发到Neutron节点，但此时Neutron节点上还没有一个终端可以用于接收VM1实例的数据。因此还需要在Neutron节点上创建一个router，并且还需要将创建的Router绑定到private网络，用于对接vxlan-1隧道网络。

在Neutron节点上创建router后，理论上VM1实例的数据就已经能够正常访问到router，但此时VM1实例的数据仍无法访问到其他网络，因为router作为一个虚拟路由器，它需要桥接到一个物理网卡上以接入物理网络，实验环境中通过router实现VM1实例的互联网访问，因此将router桥接到ens33网卡上。在两个节点上使用`brclt show`即可观察到网桥信息。

## 四、Provider networks网络模型（仅作演示）

**此配置属于不合规操作，仅作学习理解演示作用**

目前的实验环境中使用Self-service networks网络模型，这种网络模型的特点在于，从创建租户网络到创建外部网络的过程，所有步骤都不可省略，所有实例的流量都需要通过Neutron节点出站，这可能会对Neutron节点造成较大压力，这个问题可以通过分布式router解决，或使用provider networks网络模型解决。provider networks模型的网络隔离通过物理网络VLAN实现，相比较之下Self-service networks使用VXLAN实现网络隔离

在OpenStack官方指南上仅描述了每种网络模型的单一的配置步骤，在本实验环境中通过同时配置provider networks和Self-service networks模型来描述两种模型的差异，但在VMware Workstation虚拟化环境下无法对provider networks模型进行验证

在OpenStack官方指南对于provider networks模型的配置中，关于Neutron服务的`/etc/neutron/plugins/ml2/ml2_config.ini`配置文件如下：

```bash
[ml2]
type_drivers = flat,vlan    # 在现有的配置文件中，已经配置了vlan类型
tenant_network_types =      # provider networks模型的租户网络类型指定为空，为空表示禁用租户自定义网络，即禁用Self-service networks
```

**此配置属于不合规操作，仅作学习理解演示作用**

1. 通过VMware Workstation为Controller和Compute节点添加一块网卡，单独用于测试provider networks模型

2. 配置新网卡“ens38”

   ```bash
   [root@controller ~]# nmcli connection delete "Wired connection 1"
   [root@controller ~]# nmcli connection add type ethernet ifname ens38 con-name ens38 autoconnect yes ipv4.method manual ipv4.addresses 10.0.0.1/24
   [root@controller ~]# nmcli connection show
   ```

3. 基于Self-service networks模型的配置文件进行修改，Neutron与Compute节点都需要修改

   ```bash
   [root@controller ~]# vim /etc/neutron/plugins/ml2/ml2_conf.ini
   [ml2]
   type_drivers = flat,vlan,vxlan    # 需要同时具备vlan和vxlan参数
   
   [ml2_type_vxlan]    # 此选项需要type_drivers选项具备vxlan参数的情况下，才会有效
   vni_ranges = 1:1000
   
   [ml2_type_vlan]     # 新增vlan相关配置
   network_vlan_ranges = default:1:1000    # 为vlan网络命名为default，并划分vlan标签ID1~1000
   
   [root@controller ~]# vim /etc/neutron/plugins/ml2/linuxbridge_agent.ini
   [linux_bridge]
   physical_interface_mappings = provider:ens33,default:ens38    # 存在多个映射的情况下，用“,”号分隔
   ```
