# Nova

Nova服务是OpenStack最核心的服务，负责维护和管理云环境的计算资源，OpenStack作为IaaS的云操作系统，实例的生命周期管理也是通过Nova服务实现的，从OpenStack架构图中可以看到Nova服务出于OpenStack架构的中心，其他组件都为Nova服务提供支持，例如Glance为VM提供image、Cinder和Swift分别为VM提供块存储和对象存储、Neutron为VM提供网络连接

## Nova架构

![Nova架构](F:/github/Linux-Server/openstack/image/Nova架构.png)

Nova的架构比较复杂，包含很多组件，这些组件以守护进程（后台daemon进程）的形式运行，可以分为以下几类：

> **API**

**nova-api**

用于接收和响应客户端的API调用请求，并分析客户端请求的参数是否合法，例如，一个创建虚拟机的请求需要具备vCPU、vMEM、vDisk等参数，nova-api服务需要分析客户端请求是否具备这些参数、参数值是否正常等，所有组件的API服务都部署在Controller节点上

> **Compute Core**

**nova-compute**

管理VM实例的核心组件，这个组件运行在计算节点上，此组件需要通过Driver对接虚拟化技术，从而实现对虚拟机的管理，例如nova-compute对接KVM虚拟化技术，它需要使用专门用于对接KVM的Driver。在OpenStack逻辑结构图中，nova-compute服务有一个箭头向下指向Hypervisor，即指向虚拟化宿主机，所有的虚拟机都运行在Hyperviros上，nova-compute需要通过调用Hypervisor API来实现对虚拟机实例的生命周期管理

**nova-schduler**

VM调度组件，用于决定在哪个计算节点上运行VM，起到资源调度作用。例如，客户端要创建一个虚拟机实例时，这个实例将来要运行在哪个计算节点上，就需要通过nova-schduler来调度，nova-schduler有一些filter（过滤器）来帮助选择一个计算节点，通过filter可以选择通过CPU剩余资源、MEM剩余资源、CPU的使用率等阈值作为判断条件来进行调度

**hypervisor**

计算节点上运行的虚拟化管理程序，虚拟机管理最底层的程序。不同虚拟化技术提供自己的hypervisor，常见的hypervisor包括KVM、Xen、VMware等

**nova-conductor**

nova-conductor用于解耦数据库。nova-compute组件经常需要更新数据库，例如客户端向nova-api发起一个创建虚拟机实例的请求，那么关于该实例的一些资源信息就需要写入数据库，出于安全性和伸缩性的考虑，nova-compute并不会直接访问数据库，而是将这个任务委托给nova-conductor，此时nova-api会将客户端的请求消息发送到Queue，在通过nova-conductor从Queue中订阅、消费数据消息，再由nova-conductor将实例的资源信息写入nova-database

除了nova-api服务以外，nova组件内的其他一些服务，例如nova-cert、nova-compute等服务也都是将数据先写入Queue，由nova-conductor从Queue中消费数据再写入nova-database的，因此nova-conductor服务的功能就是解耦数据库

> **Console Interface**

**nova-cert**

与证书相关的数据和操作由nova-cert服务处理，提供x509证书支持

**nova-console**

通过Web console登录管理实例之前需要先配置VNC，而VNC最终也是调用到了nova-console服务，用户可以通过多种方式访问实例的控制台

nova-novncproxy：基于Web浏览器的VNC访问

nova-spicehtml5proxy：基于HTML5浏览器的SPICE访问

nova-xvpnvncproxy：基于Java客户端的VNC访问

**nova-consoleauth**

负责对访问VM控制台请求提供Token认证

> **Database**

**nova-database**

用于关联数据库

>**Message Queue**

Nova服务下包含众多组件，各个组件之间需要相互协调和通信，为了解耦各个组件，Nova通过Message Queue作为组件的信息中转站，在Nova架构图中可以看到各个组件之间都是通过Message Queue是实现通信的

nova服务中最重要的组件有4个：nova-api用于接收和响应客户端请求；nova-scheduler通过filter调度选择合适的nova-compute创建客户端需要的实例；nova-compute用于对接Hypervisor从而实现对实例的管理；nova-conductor实现数据库的解耦

但从OpenStack逻辑结构图中还能看到nova组件中还有一个不同的信息，在此前的组件中都没有遇到过，就是nova需要去连接rabbitmq，例如Glance组件中没有用到Queue，此前的配置中也不涉及Queue。在nova组件中，各个服务之间需要通过Queue实现通信，因此在nova的配置文件中需要定义rabbitmq相关的配置

除了nova-compute服务是部署在计算节点上，nova组件中的其他所有服务都是部署在Controller节点上，因此部署nova组件时需要在两个节点上同时部署，首先需要在Controller节点上完成nova节点的API服务以及API服务所对应的EndPoint的创建，其次在计算节点上配置nova-compute，例如通过什么Driver对接什么虚拟化技术，因此在查看OpenStack官方指南的时候，关于nova组件的部署在官方指南上也分为了Controller节点与Compute节点的配置

## Nova部署

### 一、先决条件

1. 数据库配置；Nova服务的数据库配置在Controller节点上配置

   ```bash
   # 1.登录MariaDB
   [root@controller ~]# mysql -uroot -predhat
   
   # 2.创建名为placement的数据库
   MariaDB [(none)]> CREATE DATABASE nova_api DEFAULT CHARACTER SET utf8;
   MariaDB [(none)]> CREATE DATABASE nova DEFAULT CHARACTER SET utf8;
   MariaDB [(none)]> CREATE DATABASE nova_cell0 DEFAULT CHARACTER SET utf8;
   
   # 3.创建placement账户并授权
   MariaDB [(none)]> GRANT ALL PRIVILEGES ON nova_api.* TO 'nova'@'localhost' IDENTIFIED BY 'openstack_nova';
   MariaDB [(none)]> GRANT ALL PRIVILEGES ON nova_api.* TO 'nova'@'%' IDENTIFIED BY 'openstack_nova';
   
   MariaDB [(none)]> GRANT ALL PRIVILEGES ON nova.* TO 'nova'@'localhost' IDENTIFIED BY 'openstack_nova';
   MariaDB [(none)]> GRANT ALL PRIVILEGES ON nova.* TO 'nova'@'%' IDENTIFIED BY 'openstack_nova';
   
   MariaDB [(none)]> GRANT ALL PRIVILEGES ON nova_cell0.* TO 'nova'@'localhost' IDENTIFIED BY 'openstack_nova';
   MariaDB [(none)]> GRANT ALL PRIVILEGES ON nova_cell0.* TO 'nova'@'%' IDENTIFIED BY 'openstack_nova';
   MariaDB [(none)]> FLUSH PRIVILEGES;
   ```

2. 创建Glance服务凭证

   ```bash
   [root@controller ~]# source admin-openrc
   [root@controller ~]# openstack user create --domain default --password openstack_nova nova
   [root@controller ~]# openstack role add --project service --user nova admin
   [root@controller ~]# openstack service create --name nova --description "OpenStack Compute" compute
   [root@controller ~]# openstack service list
   ```

3. 为服务实体创建API EndPoint

   ```bash
   [root@controller ~]# openstack endpoint create --region RegionOne compute public http://controller:8774/v2.1
   [root@controller ~]# openstack endpoint create --region RegionOne compute internal http://controller:8774/v2.1
   [root@controller ~]# openstack endpoint create --region RegionOne compute admin http://controller:8774/v2.1
   [root@controller ~]# openstack catalog list
   ```

### 二、安装部署

#### Controller节点配置

1. 安装nova软件包

   ```bash
   [root@controller ~]# yum install -y openstack-nova-api openstack-nova-conductor openstack-nova-novncproxy openstack-nova-scheduler
   ```

2. 修改nova配置文件，连接数据库

   ```bash
   [root@controller ~]# vim /etc/nova/nova.conf
   [DEFAULT]
   enabled-apis = osapi_compute,metadata    # 启用的API接口参数
   transport_url = rabbit://openstack:openstack_rabbitmq@controller:5672    # 配置连接RabbitMQ的账户、密码、地址
   my_ip = 192.168.0.40    # 配置my_ip选项以使用控制器节点的管理网络IP地址
   use_neutron = true    # 启用对neutron组件服务的支持
   firewall_driver = nova.virt.firewall.NoopFirewallDriver
   allow_resize_to_same_host = true    # 此参数用于控制虚拟机实例调整资源操作的行为，默认情况下resize操作会强制将实例迁移到其他计算节点上执行资源调整（如CPU、内存、磁盘变更），配置此参数后值为true后，允许实例在原始计算节点上直接resize
   
   [api]
   auth_strategy = keystone    # API的验证通过keystone验证
   token_cache_time = 3600
   
   [api_database]
   connection = mysql+pymysql://nova:openstack_nova@controller/nova_api
   
   [database]
   connection = mysql+pymysql://nova:openstack_nova@controller/nova
   
   [glance]
   api_servers = http://controller:9292    # nova组件负责实例的整个生命周期，这其中就包括实例的创建，而创建实例则需要使用image，因此nova还需要与glance组件对接，组件与组件之间的通信全部都是通过API服务进行对接，因此在nova的配置文件里只需要定义glance组件的API即可，最终nova需要从glance上下载image
   
   [keystone_authtoken]
   www_authenticate_uri = http://controller:5000/
   auth_url = http://controller:5000/
   memcached_servers = controller:11211
   project_domain_name = Default
   user_domain_name = Default
   project_name = service
   username = nova
   password = openstack_nova
   token_cache_time = 3600
   
   [neutron]
   url = http://controller:9696
   auth_url = http://controller:5000
   auth_type = password
   project_domain_name = default
   user_domain_name = default
   project_name = service
   region_name = RegionOne
   username = neutron
   password = openstack_neutron
   service_metadata_proxy = true
   metadata_proxy_shared_secret = openstack_metadata
   
   [oslo_concurrency]
   lock_path = /var/lib/nova/tmp
   
   [vnc]
   enabled = true    # 启用VNC功能，nova-console服务就是专门为VNC提供服务的，只有配置了VNC，才能通过Web Console访问VNC的管理页面
   server_listen = $my_ip    # VNC服务监听的地址
   server_proxyclient_address = $my_ip    # 配置代理的客户端地址。VNC的服务运行在Controller节点上，但实例实际上运行在Compute节点上，客户通过Horizon去访问Web Console时，实际上会先访问到Controller节点上的VNC服务，然后由Controller节点代理访问Compute节点
   novncproxy_host = 0.0.0.0    # 监听节点的所有接口。未配置或配置为127.0.0.1时，仅允许本机访问，外部用户无法访问VNC代理服务；配置为具体IP时，如果涉及到主机节点的迁移时，IP会发生变化，配置为具体IP可能导致服务无法正常运行或外部用户访问VNC代理异常
   novncproxy_port = 6080
   novncproxy_base_url = http://controller:6080/vnc_auto.html    # 客户通过Horizon去访问Web Console时，会跳转到此URL，通过Controller节点代理访问Compute节点
   
   [placement]    # 专门用于统计资源信息，统计后的信息仍需要通过placement账户进行上传
   region_name = RegionOne
   project_domain_name = Default
   project_name = service
   auth_type = password
   user_domain_name = Default
   auth_url = http://controller:5000/v3
   username = placement
   password = openstack_placement
   
   [scheduler]
   discover_hosts_in_cells_interval = 180    # 每180秒周期性自动发现计算节点。在Cell v2架构中，新部署的计算节点（nova-compute）不会自动注册到调度器，需要手动执行nova-manage cell_v2 discover_hosts命令将新增计算节点（nova-compute）加入host_mappings表，使其可被调度。此参数的作用就是每180秒自动执行一次nova-manage自动发现命令
   ```

   nova配置文件中关于RabbitMQ的配置一定要正确，从此前的Nova组件内部服务通信学习中，Nova组件内部服务都需要通过RabbitMQ进行通信

3. 初始化nova数据库

   ```bash
   [root@controller ~]# su -s /bin/sh -c "nova-manage api_db sync" nova
   [root@controller ~]# su -s /bin/sh -c "nova-manage cell_v2 map_cell0" nova
   [root@controller ~]# su -s /bin/sh -c "nova-manage cell_v2 create_cell --name=cell --verbose" nova
   [root@controller ~]# su -s /bin/sh -c "nova-manage db sync" nova
   [root@controller ~]# su -s /bin/sh -c "nova-manage cell_v2 list_cells" nova
   ```

4. 启用nova服务

   ```bash
   [root@controller ~]# systemctl enable --now openstack-nova-api openstack-nova-scheduler openstack-nova-conductor openstack-nova-novncproxy
   ```

#### Compute节点配置

Compute节点的配置文件可以直接复用Controller节点的配置文件，两者的安装步骤也是与其他OpenStack组件的安装步骤基本一致，需要注意的是，Compute节点上必须要能够支持虚拟化技术，所有的实例都是运行在Compute节点上的

1. 安装nova软件包

   ```bash
   [root@compute ~]# yum install -y openstack-nova-compute
   ```

2. 修改nova配置文件

   Controller节点上的Nova配置文件与Compute节点上的Nova配置文件基本上非常相似，仅少量配置存在差异需要手动修改

   相比较Controller节点与Compute节点的配置文件，主要需要修改的两大块部分分别是VNC相关配置和数据库相关配置，从OpenStack逻辑结构图中可以看到，nova-compute节点服务本身是不直接连接数据库的，而是通过Queue和nova-conductor实现与数据库的数据交互，因此nova-compute节点中需要删除所有连接数据库的配置

   ```bash
   [root@compute ~]# scp -r root@controller:/etc/nova/nova.conf /etc/nova/
   [root@compute ~]# vim /etc/nova/nova.conf
   [DEFAULT]
   my_ip = 192.168.0.41    # 修改为Compute节点的管理平面IP
   
   [api_database]
   # connection = mysql+pymysql://nova:openstack_nova@controller/nova_api    # 删除或注释此行
   
   [database]
   # connection = mysql+pymysql://nova:openstack_nova@controller/nova    # 删除或注释此行
   
   [vnc]
   server_listen = 0.0.0.0    # VNC服务监听Compute节点上的所有IP
   novncproxy_base_url = http://controller:6080/vnc_auto.html    # 指定了用户通过浏览器访问虚拟机VNC控制台的代理服务入口地址。通过Horizon点击VNC服务时会弹出此链接
   ```

3. 完成安装

   ```bash
   [root@compute ~]# egrep -c '(vmx | svm)' /proc/cpuinfo    # 确认Compute节点是否支持KVM虚拟化
   [root@compute ~]# lsmod | grep kvm    # 检查Compute节点是否已加载KVM模块
   
   # 启用服务
   [root@compute ~]# systemctl enable --now libvirtd openstack-nova-compute
   ```

   在OpenStack官方指南中有说明，当egrep指令返回的值为1或更大，则Compute节点支持硬件辅助的虚拟化，通常不需要额外的配置。若egrep指令返回的值为0，则Compute节点不支持硬件辅助的虚拟化，此时必须配置libvirt使用QEMU而不是KVM

   ```bash
   [libvirt]
   virt_type = qemu    # 注：此配置仅限于Compute节点不支持KVM虚拟化时配置，配置此参数意味着Compute节点将使用纯软件的全虚拟化技术，在性能上远低于KVM虚拟化。启用此参数后就与KVM没有关联了
   ```

4. 在Controller节点上验证nova-compute服务

   ```bash
   [root@controller ~]# source admin-openrc
   [root@controller ~]# openstack compute service list --service nova-compute    # 查看nova-compute服务是否正常
   +----+--------------+---------------------+------+---------+-------+----------------------------+
   | ID | Binary       | Host                | Zone | Status  | State | Updated At                 |
   +----+--------------+---------------------+------+---------+-------+----------------------------+
   |  5 | nova-compute | compute.example.com | nova | enabled | up    | 2025-05-15T15:36:04.000000 |
   +----+--------------+---------------------+------+---------+-------+----------------------------+
   [root@controller ~]# openstack compute service list    # 查看所有的nova服务是否正常，包括nova-conductor、nova-scheduler、nova-compute服务
   ```

   验证nova的各个组件正常，则代表nova服务正常

5. 在Controller节点配置查找计算主机

   ```bash
   [root@controller ~]# su -s /bin/sh -c "nova-manage cell_v2 discover_hosts --verbose" nova
   ```

   此操作类似于在Controller节点上注册计算节点，如果计算节点需要进行扩容，仍需要同步配置此命令

6. 检查cells和Placement API是否正常工作，以及其他必要的先决条件是否到位

   ```bash
   [root@controller ~]# nova-status upgrade check
   ```

至此，Compute节点的安装已经完成，但还有一个问题，此前理论知识中有提到过，nova-compute服务是需要直接对接Hypervisor的，且nova-compute可以通过不同的Driver来对接不同的Hypervisor，但在Compute节点上修改nova配置文件时却没有调整到有关于Driver的参数选项，这是因为Nova默认就是使用KVM虚拟化，如果要对接其他的虚拟化技术，则必须要具备相应的Driver。例如，nova-compute服务默认情况下不支持esxi，需要对接esxi的话需要单独配置Driver

```bash
vim /etc/nova/nova.conf
[libvirt]
# kvm - <No description provided>
# lxc - <No description provided>
# qemu - <No description provided>
# uml - <No description provided>
# xen - <No description provided>
# parallels - <No description provided>
#virt_type=kvm    # 默认使用KVM虚拟化
```
