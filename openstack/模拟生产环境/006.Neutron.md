# Neutron

OpenStack网络使用的是一个SDN（Software Defined Networking）模块，即Neutron，SDN是一个可插拔的架构，支持插入交换机、防火墙、负载均衡器等，这些都定义在软件中，从而实现对整个云基础设施的精细化管控。组网规划中使用了三个网卡，eth0作为外部网络（在OpenStack术语中，外部网络通常被称为Provider网络），同时也用于管理网络，便于测试访问，生产环境建议分开；eth1用于Cluster Network；eth2用于Tenant网络，即vxlan网络

OpenStack网络部署方式可选的有OVS和LinuxBridge，实验环境中选择LinuxBridge模式，部署过程大同小异。Neutron服务在controller节点和compute节点上都需要安装，同时Neutron与Nova两者服务有交互，所以配置Neutron服务时还需要修改Nova服务的配置

Neutron服务相对于其他OpenStack模块服务，难度更大、更复杂，对于Neutron服务的学习需要从多个不同的维度进行描述

## Neutron架构

![Neutron架构](F:/github/Linux-Server/openstack/image/Neutron架构.png)

Neutron服务内包含了如下组件：

- Neutron Server

  对比其他OpenStack服务，Neutron服务的组件中并没有API组件，Neutron API组件的功能集成在了Neutron Server组件中，Neutron Server组件对外提供Neutron API，接收客户端请求，并调用Plugin处理请求。例如，创建网络、创建子网、创建router等请求。

- Plugin

  Neutron的Plugin按照功能又分为两类：Core Plugin 和 Service Plugin，Core Plugin维护Neutron的network、subnet、port相关资源的信息，Service Plugin提供routing、firewall、load balance等服务。无论是哪一类Plugin，它最终都是用于处理Neutron Server的请求，维护OpenStack的逻辑网络状态，并调用Agent处理请求。

  Plugin维护的是OpenStack的逻辑网络状态，它只负责将创建资源的请求信息写入到数据库并维护数据库中的信息，例如，用户发起请求要创建一个网桥，Plugin从Queue中读取到Neutron Server的请求后，会将网桥的资源信息写入数据库，但Plugin并不会真正在物理节点上创建出这个网桥，而是将Neutron Server请求的资源信息写入数据库后，再通过Queue通知运行在各个物理节点上的Agent，通过对应的Agent创建网桥。

- Agent

  真正用于具体的实现所有的网络细节，处理Plugin的请求，负责在network provider上真正实现各种网络功能。Agent本身也有多种类型，例如，L3 Agent、DHCP Agent、Linux Birdge Agent等类型，当Agent需要在OpenStack网络中实现某一种功能时，需要通过对应类型的Agent实现，例如，在子网内需要实现DHCP功能时，需要通过DHCP Agent实现。

- network provider

  提供网络服务的虚拟或物理网络设备，例如，Linux Bridge、Open vSwitch或其他支持Neutron的物理交换机

- Queue

  Neutron Server、Plugin 和 Agent 之间通过 Messaging Queue 通信和调用。

- Database

  存放OpenStack的网络状态信息，包括Network、Subnet、Port、Router等。

## OpenStack网络类型

在OpenStack官方指南的概述章节中就有提到，OpenStack架构的网络类型分两种：Provider networks 和 Self-service networks

### 一、Provider networks

直译为提供商网络，Provider networks以最简单的方式部署OpenStack Networking服务，主要提供了二层交换网络和VLAN隔离服务。从本质上讲，它将虚拟网络桥接到物理网络，并依靠物理基础设施提供三层路由网络。在Provider networks类型的网络下，用户需要知晓底层网络基础架构的更多信息，以创建与基础架构完全匹配的虚拟网络。

简单一点理解，Provider networks网络类型下，OpenStack只提供单节点下的多实例之间的二层交换网络服务，如果要实现多节点下的多实例之间的二层交换网络、三层路由网络服务，则需要通过网络基础架构来实现，即通过物理交换机、物理路由器设备来实现。因此，Provider networks类型导致OpenStack架构本身缺少对三层专用网络的支持，以及高级服务，例如LBaaS、FWaaS等。

### 二、Self-service networks

Self-service networks选项通过三层路由服务增强了Provider networks选项，这些服务使用叠加分段方法（如VXLAN）启用自助服务网络。实际上，它使用网络地址转换（NAT）将虚拟网络路由到物理网络，此选项还为FWaaS等高级服务提供了基础。OpenStack用户可以创建虚拟网络，而无需了解数据网络上的底层基础架构。如果对二层插件进行了相应的配置，这也可以包括 VLAN 网络。

整个Self-service networks选项，需要详细学习VXLAN网络知识，目前仅需要具备一个基本的认知，将VXLAN理解为类似GRE隧道的概念即可，多个虚拟交换机之间依托于三层路由，通过隧道技术实现不同物理节点上之间的实例的通信。

Self-service networks需要了解三个概念

- Tenant的网络类型

  例如VXLAN、VLAN、FLAT（扁平网络模型，所有实例都属于同一VLAN）

- Router

  租户的实例如果需要连接外网或跨网段通信，则需要通过Router提供的三层网络实现

- Provider

  通过Provider将虚拟网络映射到某个物理网络上

## Neutron配置

在配置Neutron服务之前首先需要明确一点，在此实验的OpenStack规划中，所有服务的API组件所监听的地址都是Manage地址，其次，在Neutron服务上将使用Self-service networks类型的网络，那么Self-service networks至少需要具备两个独立的网络：VXLAN网络、Router网络。VXLAN网络用于实现不同物理节点上、不同实例之间的通信；Router网络用于实现所有实例的外部访问通信。这两个独立的网络都需要单独的网络作为网桥实现，即Provider概念的实现。

### 一、OpenStack网络规划

实验环境中主要以物理网卡的方式进行配置，网桥配置也会在注释中有说明。无论使用物理网卡或网桥，除了需要修改系统本身的IP配置以外，Neurton服务中涉及到变更的配置文件只有`linuxbridge_agent.ini`，此文件在Controller节点和Compute节点的配置文件中都需要修改，在修改使用的设备类型后需要重启Neutron服务或重启系统

#### 1.1 物理网卡

在OpenStack基本环境小节中，已经按照虚拟机规划配置过所有OpenStack节点的VXLAN网卡的IP，此处可以跳转到OpenStack基本环境小节查看，或直接观察VMware虚拟机的IP配置

在所有物理节点上都需要一张网卡用于VXLAN网络，VXLAN本质上还是一个隧道网络，因此它也需要一个类似于GRE隧道配置中的隧道源IP、隧道目的IP。VXLAN网络所需要的设备可以直接使用物理网卡，或通过物理网卡新建一个VXLAN网桥，通过VXLAN网桥实现VXLAN隧道网络通信，无论使用哪种方式，VXLAN网络都需要具备一个隧道IP，两种方式本质上都是为了解决VXLAN隧道网络的通信问题

#### 1.2 网桥

1. 删除原有物理网卡配置

   ```bash
   [root@controller ~]# nmcli connection delete eth2
   
   [root@compute01 ~]# nmcli connection delete eth2
   
   [root@compute02 ~]# nmcli connection delete eth2
   ```

1. 为所有OpenStack VMware虚拟机节点准备VXLAN网络

   ```bash
   # 1.Controller节点新建网桥，用于VXLAN网络
   [root@controller ~]# nmcli connection add type bridge ifname br-vxlan con-name br-vxlan ipv4.method manual ipv4.addresses 172.16.31.40/24 autoconnect yes
   [root@controller ~]# nmcli connection add type ethernet ifname eth2 con-name eth2 master br-vxlan autoconnect yes
   [root@controller ~]# nmcli connection up eth2 && nmcli connection up br-vxlan
   [root@controller ~]# nmcli connection show
   [root@controller ~]# ip add show br-vxlan
   
   # 2.Compute01节点新建网桥，用于VXLAN网络
   [root@compute01 ~]# nmcli connection add type bridge ifname br-vxlan con-name br-vxlan ipv4.method manual ipv4.addresses 172.16.31.41/24 autoconnect yes
   [root@compute01 ~]# nmcli connection add type ethernet ifname eth2 con-name eth2 master br-vxlan autoconnect yes
   [root@compute01 ~]# nmcli connection up eth2 && nmcli connection con up br-vxlan
   [root@compute01 ~]# nmcli connection show
   [root@compute01 ~]# ip add show br-vxlan
   
   # 3.Compute02节点新建网桥，用于VXLAN网络
   [root@compute02 ~]# nmcli connection add type bridge ifname br-vxlan con-name br-vxlan ipv4.method manual ipv4.addresses 172.16.31.42/24 autoconnect yes
   [root@compute02 ~]# nmcli connection add type ethernet ifname eth2 con-name eth2 master br-vxlan autoconnect yes
   [root@compute02 ~]# nmcli connection up eth2 && nmcli connection up br-vxlan
   [root@compute02 ~]# nmcli connection show
   [root@compute02 ~]# ip add show br-vxlan
   ```
   
   VXLAN隧道网络只解决了OpenStack架构中，多Compute节点下的多实例之间的二层交换网络通信，此时实例无法对外提供服务，因此还需要Router网络实现三层路由，Router网络同样可以通过物理网卡或网桥的方式实现
   
2. Controller节点新建Router网桥
   
   Router网桥实际是在Neutron服务上构建的，计算节点上不需要Router网桥，计算节点只需要实现二层网络功能，三层网络功能由网络节点（Neutron）实现，但在此实验中将Neutron服务部署在Controller节点上，因此在Controller节点上新建Router网桥
   
   以Controller节点上的可以上网的网卡（eth0）作为Router网桥，用于实现实例的外部访问，但需要注意，从最初的配置开始到目前为止，该网卡一直处于在用状态，并且是已具备网络连接的，因此在为该网卡配置新的连接前（bridge-slave），还需要删除该网卡原本在用的网络连接（eth0），需要注意的是，此删除网络连接的操作可能会导致Controller节点断网
   
   在本实验中的基本环境配置部分，对于Controller节点的外部网络采用的是静态固定IP，那么在删除原有的eth0网络连接时，NetworkManager服务可能会自动创建一个"Wired connection 1"绑定到eth0网卡，并自动获取IP，这样子能保障系统的外部网络不会断开，但后续创建新的网络连接绑定到eth0网卡时，仍需要手动删除此"Wired connection 1"网络连接
   
   ```bash
   [root@controller ~]# nmcli connection delete eth0    # 删除原有网络连接，系统可能会自动新建一个“Wired connection 1”网络连接绑定到eth0网卡
   [root@controller ~]# nmcli connection add type bridge con-name br-router ifname br-router ipv4.method manual ipv4.addresses 192.168.31.41/24 ipv4.gateway 192.168.31.1 ipv4.dns 192.168.31.1 autoconnect yes    # 新建用于实现router功能的网桥
   [root@controller ~]# nmcli connection add type bridge-slave con-name eth0 ifname eth0 master br-router autoconnect yes    # 将Controller节点上的可以上网的网卡连接到Router网桥
   [root@controller ~]# nmcli connection up eth0    # 启用bridge-slave网络连接
   [root@controller ~]# nmcli connection delete "Wired connection 1"    # 删除系统自动创建的网络连接
   ```

### 三、安装配置

#### 3.1 Controller节点配置

安装配置时需要选择对应的网络类型的Neutron安装包，此实验中使用Self-service networks类型

1. 安装Neutron

   ```bash
   [root@controller ~]# yum install -y openstack-neutron openstack-neutron-ml2 openstack-neutron-linuxbridge ebtables
   ```

2. 修改neutron配置文件

   ```bash
   [root@controller ~]# cp /etc/neutron/neutron.conf{,.bak}
   [root@controller ~]# grep -Ev "^$|^#" /etc/neutron/neutron.conf.bak > /etc/neutron/neutron.conf
   [root@controller ~]# chown root.neutron /etc/neutron/neutron.conf.bak
   
   [root@controller ~]# vim /etc/neutron/neutron.conf
   [DEFAULT]
   core_plugin = ml2    # ml2作为Core Plugin，用于实现二层通信
   service_plugins = router    # router是Self-service networks类型必须具备的Service Plugin，实例需要通过router插件实现外部访问
   allow_overlapping_ips = true    # 允许多个Tenant创建并使用相同的私有IP地址范围
   transport_url = rabbit://openstack:openstack_rabbitmq@controller
   auth_strategy = keystone
   notify_nova_on_port_status_changes = true    # 与实例端口状态变化相关，会影响到实例的启动
   notify_nova_on_port_data_changes = true    # 与实例的安全组、IP/MAC、绑定等配置相关，会影响到实例的实时配置更新
   
   [database]
   connection = mysql+pymysql://neutron:openstack_neutron@controller/neutron
   
   [keystone_authtoken]
   www_authenticate_uri = http://controller:5000
   auth_url = http://controller:5000
   memcached_servers = controller:11211
   auth_type = password
   project_domain_name = default
   user_domain_name = default
   project_name = service
   username = neutron
   password = openstack_neutron
   token_cache_time = 3600    # 默认值为300，单位为秒。此参数用于控制Neutron服务缓存Keystone认证令牌的时长，强烈建议确保 此参数的值小于Keystone服务配置文件的expiration值
   
   [nova]
   auth_url = http://controller:5000
   auth_type = password
   project_domain_name = default
   user_domain_name = default
   region_name = RegionOne
   project_name = service
   username = nova
   password = openstack_nova
   
   [oslo_concurrency]
   lock_path = /var/lib/neutron/tmp
   ```

   在没有安装Nova服务的情况下，先在Neutron服务的配置文件中加入了nova模块的配置，nova模块的配置不会被使用，所以也不会报错

3. 配置Neutron的Modular Layer 2（ml2）二层插件

   ```bash
   [root@controller ~]# cp /etc/neutron/plugins/ml2/ml2_conf.ini{,.bak}
   [root@controller ~]# grep -Ev "^$|^#" /etc/neutron/plugins/ml2/ml2_conf.ini.bak > /etc/neutron/plugins/ml2/ml2_conf.ini
   [root@controller ~]# chown root.neutron /etc/neutron/plugins/ml2/ml2_conf.ini.bak
   
   [root@controller ~]# vim /etc/neutron/plugins/ml2/ml2_conf.ini
   [ml2]
   type_drivers = flat,vlan,vxlan    # 类型驱动，代表ml2插件支持什么网络类型
   tenant_network_types = vxlan    # 租户网络类型，明确指明ml2插件支持租户网络类型是vxlan
   mechanism_drivers = linuxbridge,l2population    # 用于指定网络功能的实现方式，例如linuxbridge意味着二层虚拟交换机使用Linux Bridge的方式实现，并且会自动创建Linux Bridge Agent，如果是OVS则生成OVS的Agent
   extension_drivers = port_security    # 支持安全组功能
   
   [ml2_type_flat]
   flat_networks = provider    # 此前提到过通过Provider可以将虚拟网络映射到某个物理网络上，此参数仅定义了flat的网络名称是provider，还没有配置provider所映射的物理网络的具体参数
   
   [ml2_type_vxlan]
   vni_ranges = 1:1000    # 租户网络选择vxlan的前提下，此参数用于设置vxlan的编号范围，vxlan的编号范围可以大于4096
   
   [securitygroup]
   enable_ipset = true    # 利用Linux内核模块ipset高效管理安全组规则，用于优化安全组规则的执行效率。ipset能够大幅减少iptables规则的数量，但需要计算节点上必须安装ipset软件包
   ```

   在明确指定`tenant_network_types = vxlan`的情况下，后续就必须配置一个隧道，同时在二层插件里需要定义`mechanism_drivers = linuxbridge`，这个参数意味着OpenStack会自动创建Linux Bridge Agent

4. 配置linux bridge agent插件

   ```bash
   [root@controller ~]# cp /etc/neutron/plugins/ml2/linuxbridge_agent.ini{,.bak}
   [root@controller ~]# grep -Ev "^$|^#" /etc/neutron/plugins/ml2/linuxbridge_agent.ini.bak > /etc/neutron/plugins/ml2/linuxbridge_agent.ini
   [root@controller ~]# chown root.neutron /etc/neutron/plugins/ml2/linuxbridge_agent.ini.bak
   
   [root@controller ~]# vim /etc/neutron/plugins/ml2/linuxbridge_agent.ini
   [linux_bridge]
   physical_interface_mappings = provider:eth0    # 此参数用于指定在ml2配置文件中定义的flat网络名称（provider），其所对应的外部网络可以指定物理网卡或网桥，若指定为网桥则应该修改为provider:br-router
   
   [vxlan]    # 配置隧道端口
   enable_vxlan = true    # 如果要禁用vxlan，则设置为false，同时注释local_ip和l2_population
   local_ip = 172.16.31.40    # 用于VXLAN网络的设备的IP，指定隧道源IP。此处仅需提供用于VXLAN网络的IP，无需直接绑定设备，因此无论实际设备是物理网卡或网桥，提供用于VXLAN网络的IP即可，此处应该取eth2网卡的IP，如果VXLAN网络使用的是网桥，此处应该取br-vxlan网桥的IP
   l2_population = true
   
   [securitygroup]    # 启用安全组
   enable_security_group = true
   firewall_driver = neutron.agent.linux.iptables_firewall.IptablesFirewallDriver    # 配置LinuxBridge iptables驱动
   
   [root@controller ~]# vim /etc/sysctl.conf    # 修改内核参数，确保内核支持网桥过滤器
   net.bridge.bridge-nf-call-iptables = 1
   net.bridge.bridge-nf-call-ip6tables = 1
   [root@controller ~]# modprobe br_netfilter    # 加载网桥过滤器模块
   [root@controller ~]# sysctl -p    # 加载内核参数
   ```

5. 配置layer-3 agent三层插件

   ```bash
   [root@controller ~]# cp /etc/neutron/l3_agent.ini{,.bak}
   [root@controller ~]# grep -Ev "^#|^$" /etc/neutron/l3_agent.ini.bak > /etc/neutron/l3_agent.ini
   [root@controller ~]# chown root.neutron /etc/neutron/l3_agent.ini.bak
   
   [root@controller ~]# vim /etc/neutron/l3_agent.ini
   [DEFAULT]
   interface_driver = linuxbridge
   ```

6. 配置DHCP agent插件

   ```bash
   [root@controller ~]# cp /etc/neutron/dhcp_agent.ini{,.bak}
   [root@controller ~]# grep -Ev "^$|^#" /etc/neutron/dhcp_agent.ini.bak > /etc/neutron/dhcp_agent.ini
   [root@controller ~]# chown root.neutron /etc/neutron/dhcp_agent.ini.bak
   
   [root@controller ~]# vim /etc/neutron/dhcp_agent.ini
   [DEFAULT]
   interface_driver = linuxbridge
   dhcp_driver = neutron.agent.linux.dhcp.Dnsmasq
   enable_isolated_metadata = true    # 启用隔离元数据，使实例可以通过Provider网络访问元数据
   ```

7. 配置metadata agent插件

   ```bash
   [root@controller ~]# cp /etc/neutron/metadata_agent.ini{,.bak}
   [root@controller ~]# grep -Ev "^$|^#" /etc/neutron/metadata_agent.ini.bak > /etc/neutron/metadata_agent.ini
   [root@controller ~]# chown root.neutron /etc/neutron/metadata_agent.ini.bak
   
   [root@controller ~]# vim /etc/neutron/metadata_agent.ini
   [DEFAULT]
   nova_metadata_host = controller    # 设置元数据主机
   metadata_proxy_shared_secret = openstack_metadata    # 设置元数据共享密码，这个密码会被用在nova服务的配置文件中
   ```

   至此，Neutron网络服务的配置基本已经完成，此前提及过Neutron与Nova要互通，所以现在还需要对Nova的配置文件进行修改，而修改Nova服务的配置文件的前提是先安装Nova服务

8. 配置nova服务使用neutron服务

   Nova服务具体的安装部署步骤会在Nova服务章节详细描述，此处仅用于提前修改与Neutron服务相关的配置

   ```bash
   [root@controller ~]# yum install -y openstack-nova-api openstack-nova_conductor openstack-nova-novncproxy openstack-nova-scheduler
   [root@controller ~]# cp /etc/nova/nova.conf{,.bak}
   [root@controller ~]# grep -Ev "^$|^#" /etc/nova/nova.conf.bak > /etc/nova/nova.conf
   ```

9. 完成安装

### 四、验证

1. 在Controller节点上检查所有的neutron插件状态是否正常

   ```bash
   [root@controller ~]# openstack network agent list
   ```

   L3 agent提供路由、DHCP agent提供DHCP地址自动分配、metadata agent提供元数据代理，这三个agent插件只会运行在Neutron节点上，在实验规划中运行在Controller节点上

2. 验证vxlan隧道

   仅查看Neutron服务的插件状态是无法直观判断出vxlan网络是否配置正常的，此时可以提前创建一个自定义的网络进行验证vxlan

   ```bash
   [root@controller ~]# openstack network create selfnet    # 创建一个网络，名称为selfnet。创建子网的回显信息中会显示网络类型为vxlan
   [root@controller ~]# openstack subnet create selfservice --network selfnet --dns-nameserver 8.8.8.8 --gateway 172.16.31.254 --subnet-range 172.16.31.0/24    # 为selfnet网络分配一个子网地址范围，该子网命名为selfservice
   [root@controller ~]# openstack subnet list    # 查看子网列表
   [root@controller ~]# brctl show    # 可以观察到新增了一个网桥，网桥下产生了一个tap接口和vxlan接口
   [root@controller ~]# ip add show    # 观察tap接口的master桥 与 vxlan接口的master桥
   ```

3. 创建一个外部网络

   ```bash
   # 创建一个虚拟网络，并命名为public
   [root@controller ~]# openstack network create public --share --external --provider-network-type flat --provider-physical-network provider
   	--share：允许所有Tenant共享此网络。若不指定此参数，网络仅创建者Project可见
   	--external：将网络定义为外部网络，使实例可以通过此网络访问互联网或外部物理网络
   	--provider-network-type：指定网络类型是Flat，即无VLAN标签的扁平型网络，直接映射到物理接口
   	--provider-physical-network：指定物理网络名称（此处为provider），将虚拟网络绑定到主机物理网卡（此处为eth0）
   	public：自定义唯一网络名称，用于其他网络相关操作，如创建子网、路由器网关等
   
   # 为public网络创建一个子网，此网络用于外部网络，因此子网IP需要外部网络的IP范围
   [root@controller ~]# openstack subnet create internet --network public --allocation-pool start=192.168.31.70,end=192.168.31.79 --dns-nameserver 223.5.5.5 --gateway 192.168.31.1 --subnet-range 192.168.31.0/24
   	internet：创建的子网名称
   	--network：指定子网所属的虚拟网络名称（此处为public），此网络必须已通过openstack network create预先创建
   	--allocation-pool：限定DHCP动态分配IP地址范围。此地址范围需要保留两个同网段的IP，一个给物理交换机、一个给网关
   	--dns-nameserver：指定DNS服务地址。223.5.5.5是阿里云公共DNS服务地址
   	--gateway：设置子网的默认网关。网关IP需要在subnet-range范围内
   	--subnet-range：采用CIDR格式定义子网地址范围
   	
   # 创建并配置一个指定IP地址的虚拟网络端口
   [root@controller ~]# openstack port create internet_port --network public --fixed-ip subnet=internet,ip
   -address=192.168.31.49
   	internet_port：创建的端口名称。不显示指定端口名称时，OpenStack会自动生成UUID作为唯一标识
   	--network：指定端口所关联的虚拟网络名称
   	--fixed-ip：指定端口关联的子网名称，以及手动指定端口的固定IP
   	
   [root@controller ~]# openstack network list    # 查看虚拟网络列表
   [root@controller ~]# openstack subnet list     # 查看子网列表
   [root@controller ~]# openstack port list       # 查看端口列表
   
   [root@controller ~]# openstack port delete internet_port    # 删除端口
   [root@controller ~]# openstack subnet delete selfservice    # 删除子网
   [root@controller ~]# openstack network delete selfnet       # 删除虚拟网络
   ```

   在`linuxbridge_agent.ini`文件中的`physical_interface_mappings = provider:eth0`，所以当前创建的flat类型的物理网络`--provider-physical-network`要指定为provider；删除网络存在先后顺序，即删除子网下的网络接口->删除子网->删除网络
